A role-based expense reporting app where employees submit receipt-backed expenses, high-value claims receive Department Head approval, and Finance tracks payment after approval. The app includes an auditable action history and a concise operational dashboard.

## User Profiles

Establish the Employee, Department Head, and Finance user groups that will receive tailored access later in the build.

Create shell custom profile files only, with no ModulePermissions yet: Employee (non-portal custom profile; intended to create expenses, see and edit only their own eligible records, and view their own status), Department_Head (non-portal custom profile; intended to review expenses specifically routed to them and approve or reject high-value submissions), and Finance (non-portal custom profile; intended to view all approved expenses and maintain payment state). Do not create default Administrator/Developer/Read/Write/Customer profiles. Do not create roles or sharing rules.

## Department_Heads

Maintain a clean directory of approvers so employees can select the correct Department Head when submitting a high-value expense.

Create form Department_Heads with fields: Directory_Details section; Head_Name text, must have; Head_Email email, must have and unique; Department text, must have; Active checkbox with initial value true. Use medium-width balanced layout and standard add/edit actions. Create default list report Active_Department_Heads over records where Active == true, showing Head_Name, Head_Email, Department, Active; filters Department and Active; sort Head_Name ascending. No workflows. This directory is maintained by Finance and available as a lookup source to employees.

## Expense_Reports

Let employees submit receipts and route each claim based on amount, while Department Heads make final decisions on high-value expenses and Finance tracks payment.

Create form Expense_Reports. Fields: Expense_Details section; Expense_Number autonumber starting at 1; Expense_Date date, must have, initial value ${zoho.currentdate}; Category picklist, must have, values Travel, Meals, Lodging, Office Supplies, Training, Client Entertainment, Other; Amount USD currency, must have, decimalplace 2, maxchar 12; Receipt upload file, must have, file count 1, browse local_drive/google_docs/zoho_docs; Description textarea; Approval_and_Payment section; Department_Head lookup to Department_Heads.ID, must have, displayformat Head_Name, searchable true; Approval_Status picklist with values Pending Department Head, Approved, Rejected and initial value Approved; Payment_Status picklist with values Not Ready, Unpaid, Processing, Paid and initial value Unpaid; Submitted_By email with initial value ${zoho.loginuserid}; Approved_or_Rejected_By email; Decision_Date date; Decision_Notes textarea; Payment_Reference text; Paid_Date date. Set record owner = Added_User. Standard add/edit actions and success message.
Create form workflow Expense_Reports_On_Validate on add/on validate: reject Amount <= 0; prevent future Expense_Date; require a valid active Department_Head lookup. Create Expense_Reports_On_Success on add/on success: if Amount > 500 set Approval_Status to Pending Department Head and Payment_Status to Not Ready; otherwise set Approval_Status to Approved and Payment_Status to Unpaid. Create on-load workflow Expense_Reports_On_Load for add/edit that disables all status, decision, submitter, payment reference, and paid-date fields for employees; Department Heads may only act through report actions; Finance may only maintain payment through report actions. Hide Department_Head for amounts at or below 500 and show it above 500, while retaining a selected value if one exists. Create Amount_On_User_Input workflow to immediately show and require Department_Head when Amount > 500, otherwise hide it; validation must enforce it only for high-value claims despite the field not being globally mandatory if necessary.
Create report button workflows Expense_Approve_Action and Expense_Reject_Action for each record. Approve only when Amount > 500, Approval_Status is Pending Department Head, and the selected Department Head email equals the logged-in user; set Approval_Status Approved, Payment_Status Unpaid, actor/date, and decision notes as appropriate. Reject under the same authorization and pending-state checks; set Approval_Status Rejected, Payment_Status Not Ready, actor/date. Create Expense_Start_Payment_Action for Finance on approved/unpaid records, setting Payment_Status Processing. Create Expense_Mark_Paid_Action for Finance on approved Processing or Unpaid records, setting Payment_Status Paid and Paid_Date current date; retain/use Payment_Reference when present. All action workflows must reject invalid state changes and create an Expense_Audit record recording the action, actor, timestamp, prior state, new state, and expense lookup.
Reports: My_Expenses default list filtered to Added_User == zoho.loginuser, columns Expense_Number, Expense_Date, Category, Amount, Approval_Status, Payment_Status, Department_Head, Receipt; filters Category, Approval_Status, Payment_Status, Expense_Date; sort Expense_Date descending. Head_Approval_Queue list filtered to Amount > 500 and Approval_Status == Pending Department Head, with Approve and Reject inline custom actions and relevant columns; access intended for Department_Head. Finance_Payment_Queue list filtered to Approval_Status == Approved and Payment_Status != Paid, with Start Payment and Mark Paid inline custom actions; columns Expense_Number, Submitted_By, Expense_Date, Category, Amount, Approval_Status, Payment_Status, Payment_Reference; group by Payment_Status, sort Expense_Date ascending; access intended for Finance. All_Expenses list for Finance showing all business and status fields, grouped by Approval_Status then Payment_Status, sorted Expense_Date descending, with total on Amount. Ensure action conditions match valid record states and action column headers match their display names.

## Expense_Audit

Keep a tamper-resistant history of approvals, rejections, and payment actions for financial accountability.

Create form Expense_Audit with Audit_Details section; Expense lookup to Expense_Reports.ID, must have, displayformat Expense_Number; Action text, must have; Actor_Email email, must have; Action_Time datetime, must have; Previous_Approval_Status text; New_Approval_Status text; Previous_Payment_Status text; New_Payment_Status text; Notes textarea. Standard actions exist structurally, but permissions later deny employee and department-head direct create/edit/delete access; records are inserted by workflows. Create default list report Expense_Audit_Trail showing Expense, Action, Actor_Email, Action_Time, previous/new approval state, previous/new payment state, Notes; filters Action, Actor_Email, Action_Time; sort Action_Time descending. No workflows.

## Expense_Dashboard

Provide a polished at-a-glance view of submitted spend, pending approvals, unpaid claims, paid claims, and recent activity.

Create page Expense_Dashboard using a responsive HTML snippet as the primary rendering approach. Include a clear header, KPI cards for total submitted amount, pending Department Head count, approved/unpaid amount, and paid amount; status badges; category spend breakdown with CSS bars; payment pipeline summary; and a recent-expenses table with links or embedded navigation to My_Expenses, Head_Approval_Queue, and Finance_Payment_Queue as appropriate. Use server-side Deluge in the snippet for aggregates and recent records, Nucleo icons only, no JavaScript and no emojis. Use ZCS components/styles where suitable and include the shared ZCS stylesheet once. Main page content must contain only layout wrappers and file references/snippet envelope; authoritative snippet content belongs under content/. Make the presentation useful across profiles, with sections gracefully showing zero values where a user has no matching records.

## Permissions

Apply complete role-appropriate access so employees, approvers, and Finance can only perform their assigned responsibilities.

Edit the Employee, Department_Head, and Finance profile files to add complete ModulePermissions, FieldPermissions, ReportPermissions, and page permissions for every form, report, and Expense_Dashboard. Employee: create Expense_Reports; view own records through My_Expenses; edit own records only while not paid and before a Department Head decision where platform permissions allow; no delete after submission; read Department_Heads lookup data; no direct Expense_Audit access; status/payment/decision fields read-only. Department_Head: read Department_Heads; read Expense_Reports routed to them through Head_Approval_Queue; no direct form create/edit/delete for decisions; permit approval/rejection report actions; read relevant status and receipt fields; no payment actions; no direct Expense_Audit form access. Finance: read all Expense_Reports and update payment through report actions; access Finance_Payment_Queue and All_Expenses; maintain Department_Heads; read Expense_Audit_Trail but cannot edit/delete audit records; no Department Head approve/reject action permission. All profiles may access Expense_Dashboard. Hide unauthorized custom buttons through profile button permissions. Include all fields and reports discovered from component files, and do not create role hierarchy.

Organize forms, reports, dashboard navigation, and record layouts into a clear web experience for each user group.

Create devices/web/menu-sections.ds with one expense-management space and sections for Dashboard, Employee Expenses, Approvals, Finance, Administration, and mandatory SharedAnalytics_Section. Map Expense_Dashboard, Expense_Reports/My_Expenses, Head_Approval_Queue, Finance_Payment_Queue, All_Expenses, Department_Heads/Active_Department_Heads, and Expense_Audit_Trail with valid finance/receipt/users/business icons. Create devices/web/theme.ds using an appropriate professional web theme with restrained blue/green financial colors and readable typography. For every report create reports/<Report>/devices/web.ds containing valid quickview and detailview layouts; fields must exist in each parent report. Include every inline custom action by its quoted display name in both quickview and detailview fields where applicable. Do not create phone or tablet configuration.
